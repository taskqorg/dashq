# dashq

dashq is one operator page for the taskqorg tools: hosts and versions, taskq boards, agent activity and agentq events from Langfuse, and serverq checks. This file holds every decision; changes follow specq [spec first](https://github.com/taskqorg/specq/blob/main/engineering/spec-first.md). No history here: decisions only, at most 200 lines.

## D1. Scope
The pull-only rules below describe the current baseline. Accepted D11 narrowly replaces the no-write, no-push and no-database restrictions for enrollment, ingestion and connection management; it does not authorize host commands.
- Read-only: dashq never writes to Langfuse, GitHub, serverq or any host. No buttons that change state.
- No new auth system: the page sits behind the existing Langfuse UI forward-auth guard (D3).
- No push channel from hosts: dashq only pulls the sources in D4. Host push is a later task (#4).
- No database: in-memory caches only; a restart rebuilds everything from the sources.
- Metadata only: never conversation text, prompts, tool input/output, raw commands, stderr/stdout or stack traces.

## D2. Process
- One Rust binary `dashq` on the shared `taskqorg/coreq` crate (release, update, launcher, service).
- `dashq serve` binds `127.0.0.1:18882` only; the port is not configurable to a non-loopback address.
- `dashq report [--period=S] [--host=H] [--agent=A] [--session=ID]` prints the `/data` JSON once (D7) for agents on the host without a browser login.
- `dashq admin WORKSPACE SUBJECT` binds a workspace administrator for enrollment (D11); `dashq profile [--window=S]` prints the profile report (D20), default window 86400 s.
- `dashq selftest` loads config, renders the fixture snapshot and reads each source once; no writes.
- `dashq --snapshot DIR` writes the fixture page as `DIR/page.html` (stylesheet inlined, no script) and `DIR/page.png`, so a reviewer sees the rendering without a browser login. PNG renderer: headless Chrome (`--headless --screenshot`, 1280 px wide), the binary from env `DASHQ_CHROME`, else `google-chrome`, `chromium`, `chromium-browser` on `PATH`, else the macOS Google Chrome app. No Chrome: `page.html` is written and the command fails naming the missing renderer. No config, no source reads.
- Baseline routes (D11 adds its explicit authenticated routes): `GET /` (page), `GET /app.js`, `GET /style.css`, `GET /data`. Any other path 404; any other method 405.
- Headers on every response: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, CSP `default-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`. No third-party assets.
- Config: a private JSON file named by env `DASHQ_CONFIG`, else `<install>/config.json` (coreq service units pass only `PATH`), mode 0600: Langfuse base URL, project id and keys, a read-only GitHub token, the project list (D4.2), the serverq report path and the host id its row joins, optional `taskq_logs` `{host: absolute taskq.log path}` (D21), the public `dash.` host name. Requests whose `Host` is not the loopback address or that name get 421 (DNS rebinding). Secrets never reach the browser, `/data`, logs or `report` output. Invalid config: the service refuses to start and names the bad key, never the value. `selftest` without any config file skips the source reads and says so.
- `dashq service install|uninstall|run` and `dashq update [--check]` are the coreq commands; `service run` is `serve` and marks the release healthy after 60 s. An `update` that makes a new release current restarts an installed service unit (unload, then load) so it runs that release; `--check`, an unchanged or a failed update leaves the service running. A failed restart exits non-zero and names the error. Automatic update (#130): an installed `service run` (the launcher runs `<install>/releases/<ver>/dashq`) checks for a newer release 900 s after start, then every 3600 s; env `DASHQ_UPDATE_EVERY` (seconds) overrides the interval, the first check waits at most 900 s. A newer release is applied by the coreq update (download, checksum, offline selftest, `current`); the service logs it and exits 75, so the unit (systemd `Restart=always`, launchd `KeepAlive`) or the Windows launcher starts the new `current`. Each check and apply prints one line to the service log (`update check: <v> available; applying`, `update: <v> applied; restarting`, `update check: up to date (<v>)`, failures with their reason); a failed check or apply keeps the running release until the next interval. Profile ops `update.check` and `update` (D20). Rollback on failed start: the release becomes healthy after 60 s; the coreq launcher restores `previous` at the third start without `healthy`. The running service then writes that version to `<install>/rolled-back` and never applies it automatically again; a newer release proceeds, a manual `dashq update` still installs it. `serve`, and `service run` of a binary outside the install, never update themselves.
- Release: CI (`.github/workflows/release.yml`) on a `v<ver>` tag equal to the `Cargo.toml` version builds static `dashq-<ver>-linux-x86_64` and `dashq-<ver>-linux-aarch64`, `SHA256SUMS` and `latest.json` into a GitHub release of `taskqorg/dashq`. Each artifact passes `selftest` with `DASHQ_SELFTEST_OFFLINE=1` before publishing; a failure publishes nothing. Every pull request runs the same two builds and selftests without publishing; `main` requires them with `tests`. Only owners push tags. Installed services take it on their own (above), other hosts with `dashq update`; rollback is coreq `previous`.

## D3. Deployment
- Runs on the production host (FRA), where Langfuse and the serverq report live.
- Served under the `dash.` host name of the Langfuse UI domain. The reverse proxy site for that name runs the same `forward_auth` guard as the Langfuse UI first, then proxies to `127.0.0.1:18882`.
- No public port: no firewall change, no listener on a public address, no route under `/api/public`, browser data including `/data` always remains guarded. D11 machine routes use their own narrow authorization instead of browser forward-auth; no wildcard exemption.
- Rollback: remove the `dash.` site block, stop the dashq service. Nothing else changes.
- dashq supersedes the agentq ServiceQ panel (`/serviceq`); its removal is agentq's task, not dashq's.

## D4. Sources
Each source has its own cache, single flight (one read in progress, callers share it) and a 10 s timeout per HTTP call.

### D4.1 Langfuse API
- Public API with the project keys, server side only. Model activity: every `GENERATION` observation (a Langfuse type, not an event name), whatever its producer.
- Agents sources: the agentq observations (agentq.md § 6), one span per event, span name = event name: `agentq.compress` (core optimization accounting, D17), `agentq.run` (RTK runs), `agentq.retrieval` (MCP tool calls), `agentq.installation` (hourly heartbeat) and `agentq.incident`. Each carries `agentq.installation` (fleet key: one installation, one row), `agentq.version`, `agentq.runtime`, `host.name` and `agentq.stage`; the Agents view takes fleet, versions, last seen and health from them, usage from `agentq.run`/`agentq.retrieval`, incidents from `agentq.incident`. Last seen is the newest event time per installation; an installation without an `agentq.installation` heartbeat in 7200 s is stale (D6).
- Periods: 30 min, 2 h, 24 h (1800, 7200, 86400 s; default 1800). Health and incident history always read 24 h. Client use (D8.4, #131) also reads `agentq.compress` and `agentq.retrieval` over 24 h (the 24 h period reuses its reads); the `agentq.installation` read takes the `io` field group, since its `agentq.routing` and `agentq.hooks` JSON strings exceed Langfuse's 200-character metadata cut.
- Cursor pagination, at most 10,000 rows per event name and period. Hitting the cap marks that source `incomplete` (D6).
- Cache 30 s per period: page loads inside 30 s share one read.

### D4.2 GitHub: boards and taskq heartbeats
- Projects: an explicit list in config (`taskqorg/taskq`, `taskqorg/agentq`, `taskqorg/serverq`, `taskqorg/coreq`, `taskqorg/specq`, `taskqorg/dashq`). Repositories are never discovered.
- Boards: open issues labelled `taskq`, one page of 100 per repo; state from the projected `q-<state>` label, priority from `p0|p1|p2`. More than 100 marks the board `incomplete`. dashq does not fold comments: a label can lag the log by one service pass.
- Heartbeats: open issues labelled `taskq-host` (`taskq host <name>`): `version <v>`, `#<N> <attempt>` lines. Age = response `Date` minus issue `updated_at`, never the local clock.
- Latest releases: `releases/latest` per project repo, cached 10 min.
- Cache 60 s per repo. A `403`/`429` rate limit keeps the last value as unconfirmed (D6) until reset.
- Snapshot adapter ([S3 R1](docs/design/adapters.md#s3-taskq-snapshots-and-questions)): with config `taskq.binary` (absolute path of the pinned taskq), dashq runs `taskq status --json` per project in a fresh scratch folder holding only `taskq.json` and a scratch install whose `token` is the read-only token (`TASKQ_INSTALL`; taskq reads no token variable), no HOME, incident reports off, folder removed after the run; single flight, 10 s timeout, cache 60 s. Its totals, questions (S3 shape, read-only) and failure reasons replace the label counts; heartbeats stay label reads. A failed, incomplete or unknown-schema run is a failed read with its reason (D6); `sources.taskq` lists it. Absent key: labels only.

### D4.3 serverq report
- The local `report.json` written by `serverq check` (path in optional `serverq` config). Read on every refresh; retain the last-good report in memory on failure with its original producer time, unconfirmed until a successful read. Absent config is unconfigured, distinct from a missing report. Absolute config paths and their acceptance fixtures use the target platform's path rules (D2).
- Accepted: `schema` 1 with `at` (epoch seconds), `results` (`ok|warn|unknown` per check with `detail`), `incidents`, `manual_rules`. Another schema or invalid JSON: unknown with the reason.
- Stale after 7200 s (hourly timer plus margin). Manual rules are listed as not verified, never as passed. Enrolled (#122): each `serverq-report/1` snapshot (serverq.md § 3 projection, schema 1) is its own `checks.installations` entry per installation and workspace (per-rule status, reason, `observed_at`, numeric evidence, open incidents, manual rules not verified), fills hosts row `<label>/<runtime>` (`serverq.installation`; the newest observation owns a shared row) and Attention items naming `installation`. Freshness: producer time, the same 7200 s (ServerQ sends no heartbeat between checks). Another payload schema is unknown with its reason; a revoked grant shows nothing current.

### D4.4 Resource samples
- Producer contract: agentq.md § 6 Resource samples (`agentq.resource`, one per 300 s bucket). Enrolled history (D11) is read first; Langfuse `agentq.resource` observations (with the `io` field group, else Langfuse cuts `agentq.resource.disks`) serve installations without enrolled samples. Each row names its `provenance`.
- Window = the period; raw samples, no aggregation; at most 2016 per installation (7 days of buckets), newest kept, a cut marks the row `incomplete`. Langfuse reads keep D4.1 pagination and cap.
- Per sample: CPU percent, RAM used/available/total bytes, per filesystem `id`, role, fstype, used/free/total bytes. A missing, invalid or inconsistent value is `null` with the producer's or dashq's reason; nothing is derived from other fields or the legacy disk-headroom summary.
- Current = newest sample; stale after 900 s. History shows `gaps` (over two buckets without a sample, or a stale tail), `resets` (`warmup` or `counter reset` CPU baselines) and `warmup` below three samples. A row that is not `ok` joins Attention gaps.

## D5. Refresh
- Redesign target: [shared dashboard rules W4–W6](https://github.com/taskqorg/specq/blob/main/design/dashboards.md) and D10. The mechanism below is the current baseline, not proof of stable in-place updates.
- The page fetches `/data` on load, every 60 s and on the Refresh button. No live push.
- The server renders the page shell; D13 boards use the pinned TaskQ browser renderer. Baseline: `GET /` renders the sections from the same document as `/data`; after a good `/data` fetch the page reloads its sections from `/` with the same query.
- The page shows `Updated <time>` and each source's age. A failed fetch keeps the last page and shows the error banner (D6); it never blanks values.

## D6. Unknown and stale
Every value carries the state of its source. The page never turns missing data into zero or into healthy.

- Source states: `ok` (fresh read), `stale` (read succeeded but data older than its limit), `unconfirmed` (this read failed; the previous value is shown with its time), `unknown` (no value yet, unsupported schema or not configured), `incomplete` (capped query). Each non-ok state has a one-line reason, e.g. `Langfuse: read failed (timeout), showing 14:02`.
- Freshness limits: Langfuse read 600 s; taskq heartbeat its `ttl` (300 s default); serverq report 7200 s; GitHub read 180 s.
- Display: green only for `ok` and a healthy value. `stale`, `unconfirmed`, `unknown` are gray or amber with the reason and age, never green. A missing number shows `—` with `unknown: <reason>`, never `0`. Capped counts show `≥N (capped)`.
- Counters that reset with a process restart say so; a reset is not shown as a drop.
- Historical incidents are deduplicated and never shown as current failures.
- A summary bar at the top lists every source that is not `ok`, with its reason.
- `/data` uses the same states: each section has `source: {state, at, age_s, reason, incomplete}`; unknown numbers are `null`, never `0`.

## D7. /data JSON
- `GET /data?period=1800|7200|86400&host=H&agent=A&session=ID&block=ID` returns the document the page renders; filters are optional; `block` (D11 telemetry) adds `telemetry_block` and filters nothing. Invalid parameters: 400. All sources failed: 503 with `{"error"}`; partial failure is 200 with source states.
- Top level: `schema` (2; D4.1 removal of the legacy Node fields raised it), `generated_at`, `period`, `filters`, `sources`, `hosts`, `attention`, `boards`, `resources` (D4.4: `window_s`, `from`, `to`, `bucket_s`, `aggregation`, `cap`, `rows` of `{installation, host, runtime, workspace, provenance, source, current, history}`), `agents`, `checks`, `versions` (D18), `optimization` (D17: AgentQ accounting, event-time buckets and source freshness), `agent_work` (D21).
- Session filters apply to model activity only; host health and resources keep host scope.
- It holds aggregates and evidence trace IDs, never prompts, commands, tool results, tokens or keys.
- Schema changes are additive within `schema` 2; a breaking change raises it. One declared removal within `schema` 2, not an additive change: `boards[].tasks[].session.line` and the `line` of `taskq-board/1` snapshot payloads (D13, #180).
- Agents read it with `dashq report` on the host, or through the guard with the owner's session.

## D8. Page
Approved design (#169): hosts and their state first, tasks through the shared TaskQ UI, other information on demand. The [design package](docs/design/first-screen.md) records design approval; [#170 evidence](docs/design/host-first-runtime.md) records runtime screen approval. Production qualification remains pending. English; D1–D7 privacy, scope and data contracts remain binding except the D10 source-summary placement amendment.
1. **Hosts**: the first screen is one grid using [H1–H7](docs/design/hosts.md), one machine/kind per row: online evidence and data age; TaskQ, AgentQ and ServerQ running versions with update state; Claude and Codex login state and probe age; CPU, RAM used/total, disk used/total per filesystem; running and host-assigned queued tasks. Each value keeps its source/time. Runtime `hosts[].taskq.observed_running` is nullable fresh attempt evidence; `boards[].attempts` adds canonical `host_id` and `current`, not pending assignment. Silence means unknown, not offline; a heartbeat never proves client login or service health. Missing login/queue adapters show unknown with a reason. Shared queues remain unassigned, never multiplied across hosts.
2. **Attention**: only a condition requiring a person and an identified action: expired login → that host's sign-in instructions; failed unit → its diagnostics; verified low disk → that filesystem's finding; task question → the single shared answer card. Name host/task, reason, age and action. Observation gaps, revoked connections and incident history are detail, not current failures; automatic retries and ordinary waits are not requests for a person. Preserve their non-ok meaning beside affected host values. A source outage requiring intervention may appear with its recovery action.
3. **Tasks**: selecting a host's count opens its observed tasks in the TaskQ view; a direct Tasks entry includes all configured projects and unassigned work. Reuse the tray's shared rows, counters, answers and released controls under D13/D14; retain project/board identity, state age, runtime, issue/session links, questions, failures, ready, blocked, later and Closed coverage. Missing full-workspace/control release stays an explicit gap, not a DashQ editor.
4. **Agents**: host/detail or on-demand Agents contains model use, clients, optimization and agent work. Per-model field sample counts stay separate; cost is null unless reported. [Client observation and coverage rules](docs/design/optimization-results.md#client-observations-and-coverage) preserve #116/#131; login is a separate probe.
5. **Server checks**: host/detail or Checks retains per-rule detail, incidents, linked work, numeric evidence and manual rules marked not verified. A closed task never establishes recovery.

## D11. Independent product connections
Accepted target: [enrollment C1–C7](docs/design/enrollment.md), including E1–E10, owns the end-to-end connection contract; [connection interface L1–L4](docs/design/connections.md) owns its accepted presentation. Implementation and release qualification remain pending.

- One process and one SQLite store (WAL/FULL) own grants, membership, revocations, receipts, projections, history and bounded export outbox. No extra daemon or database server.
- C3 owns browser/device routes and authority; C4 owns durable acceptance and replay; C5 owns limits. Adjust CSP only for reviewed same-origin approval forms. Keep the loopback listener; never expose read APIs through machine-route exceptions.
- D4 gains authenticated producer snapshots. Enrollment registry supplies expected installations even without recent events; optional Langfuse/GitHub sources cannot block independent product enrollment or hide committed snapshots. Legacy sources keep their provenance and never create duplicate identities by hostname.
- D6/D7 apply the authenticated actor's scope server-side, including HTML, history, evidence, exports and local report. Local report is a protected host-administrator capability, never a remote identity bypass. Freshness uses producer observation time; connection and export health remain separate.
- D8 adds approval, scoped installation overview and explicit revoke. First completion requires the same projection as the browser; resource history needs real samples. Observation grants provide no task-answer or host-command authority.
- Pairing (#34): `POST /machine/connect/device|token|ack` and `/machine/connection/revoke` per coreq wire `coreq-enrollment/1`; guarded `GET|POST /connect` approves or denies a code. The browser subject comes only from `X-Dashq-Subject`, which the proxy strips from clients and copies from the guard's verified answer ([fixture/Caddyfile](fixture/Caddyfile); source header qualified in #4). Loopback callers are host-local and trusted like `dashq report`; a proxy-only listener or shared secret is a #4 qualification item if the host has untrusted local users. Re-pairing a connected installation warns that approval replaces it. Approval needs workspace membership, the `https://<public_host>` Origin and a CSRF token bound to account and code. `dashq admin WORKSPACE SUBJECT`, run by the host administrator, creates `dashq.db` and `dashq.key` (0600) next to the config and binds the first administrator; until then enrollment routes answer 503. The token response is sealed with `dashq.key` (AES-256-GCM) and erased at ack or expiry; the store keeps only credential and device-code SHA-256 verifiers.
- Board scope (#58): `/machine/connect/device` may carry `scope` `{name: "<id>/<version>", value: <single line ≤128>}` (coreq#36); malformed is `invalid_request`. The approval page names it under Board scope; none renders as before. The grant stores it; token, ack/revoke status and receipt replies name it as `scope`. A later token, ack, ingest or receipt request naming another scope gets 403 `scope`; revoke always succeeds. Evidence: [light](docs/design/evidence/approval-scope-light.png), [dark](docs/design/evidence/approval-scope-dark.png).
- Ingestion (#35): `POST /machine/ingest` and `/machine/connection/receipt` per `coreq-enrollment/1`; DashQ runs coreq's conformance traces ([fixture/enrollment](fixture/enrollment), copied from the pinned tag with routes moved under `/machine/` by #110; #122 replaced the serverq trace placeholder payload with the minimal schema 1 projection, since only a renderable payload reads `projected`). The grant supplies installation and workspace; a schema outside the grant, or a `taskq-board/1` record whose `board` (`<kind>:<host>/<repo>`) is not the granted board scope (#126), is rejected `scope`, a payload outside the metadata allowlist (short identifier keys, numbers, booleans, short single-line strings; objects five deep, a scalar array in the fifth; no content, command, output, path or secret fields or path-like values; one owner-approved exception, #125: a `taskq-board/1` ask-card option's `text` at `tasks[].choices[].text`, still a short single-line string, because TaskQ's observation allowlist scopes choices as board content; `text` anywhere else or in another schema stays refused) `payload`, a reused event ID with other content `replay_mismatch`, a record older than the receipt window `expired`; a full store answers 503 so nothing is acknowledged. Per device 60 requests/min, burst 10. Forwarding (#37): `agentq-event/1` (payload exactly `{name, metadata}`, name one of agentq.md § 6 `agentq.installation|run|compress|retrieval|incident|resource`; DashQ's proposal; no AgentQ export-schema issue exists yet, so its handoff to AgentQ is open) enters the bounded outbox in the acceptance transaction and never becomes a snapshot; every other schema is a snapshot. With `langfuse.forward: true` a separate thread posts the oldest 100 rows of the oldest row's grant every 5 s as OTLP/JSON to that project's `/api/public/otel/v1/traces` with the server-side keys and `x-langfuse-ingestion-version: 4` (v4 `events_only` projects refuse the legacy `/api/public/ingestion`): one complete `event` span per row at producer time, metadata as `langfuse.observation.metadata.*`, DashQ ID `<installation>:<generation>:<event_id>` (`:` never occurs in either ID, so distinct events never share one) in `dashq.id`, trace and span IDs from its SHA-256, so a retry re-sends the same span. A 200 confirms the request's rows and they leave; when its OTLP `partialSuccess.rejectedSpans` is n > 0 Langfuse does not name the lost spans, so those rows leave without a resend and become one export gap of n events in that grant's workspace over their observation window (a message with zero rejected is a warning); a 4xx other than 429 resends that pass's rows one by one and each refused row becomes an export gap; outage, 5xx or unconfirmed rows stay; expiry (7 days, hourly prune) becomes a gap; a full outbox answers 503 `outbox_full` while snapshot-only batches stay accepted. Loopback `/data` adds `sources.export` (`unknown` unset or before a pass, `ok` after a confirmed pass, `stale` `export delayed: <reason>`, with `pending` and `gap_events`). A payload of two keys without `metadata` is rejected `payload`, as is an export whose `observed_at` OTLP cannot express (unsigned nanoseconds: after 2554); a pass turns any such row already queued into an export gap and never overflows. Qualified against a recorded in-process stub and live (owner-approved, tagged `test: dashq#37`) on the production Langfuse v4 project: two deliveries of each span read back as one observation in Observations API v2 once Langfuse merges (reads showed the span twice for up to 3 min, so readers must tolerate a transient duplicate); Langfuse documents no read-path deduplication guarantee, so the opt-in live check (`cargo test -- --ignored live`) is rerun after a Langfuse upgrade. Forwarding stays off by default. Data rows keep the workspace of the grant that sent them; after revoke a new approval may pick another workspace, which starts empty.
- Projection: one function serves `/data`, `dashq report` and a 2 s service pass; a receipt becomes `projected` only when that projection read its snapshot as current and a view renders it (`agentq-snapshot/1`; `serverq-report/1` with a schema 1 ServerQ projection payload; `taskq-board/1` with a schema 1 TaskQ board observation, #125: Connections shows its board, totals or the incomplete reason, and observed task count); any other schema or payload stays `accepted`. `/data` adds `installations` `{source, rows}` and `sources.enrollment` (only once set up): one row per installation and workspace from its newest grant, `connection` `active|pending|revoked`, `observation` from producer time (stale after 180 s, `serverq-report/1` after 7200 s; future time unknown, `clock uncertain`; none: `no snapshot yet`) and `snapshot` `{event_id, schema, payload}`. Scope: loopback requests and `dashq report` see all; requests to the public name see their verified subject's workspaces (administrator: all installations there; member: those it approved), none without a subject. Langfuse and GitHub config are optional; their failure never hides snapshots or turns `/data` into 503.

- TaskQ telemetry (#161, #181, taskq#1353 S1–S5): `taskq-telemetry/1` is a separate TaskQ schema the approval page lists; only a grant naming it may send it, else `scope`. Payload `{schema: 1, first, last, rows, bytes, gzip, status?}`: `first`/`last` are `{seq, id}` as taskq `telemetry_sync` sends them (a bare seq number stays accepted), naming the block's first and last line, whose seqs rise; `gzip` is the base64 gzip (≤512 KiB) of `bytes` (≤1 MiB) bytes holding `rows` JSON lines of the coreq export; every line must pass the metadata allowlist, else `payload`. `status` is the sender's `connection.telemetry` counters `backlog_rows`, `backlog_bytes`, `gap_rows` (numbers or null); taskq v4.6.30 sends none. Conformance: [fixture/taskq-telemetry](fixture/taskq-telemetry) holds the records taskq v4.6.30's unmodified sender posted. A block is stored once (C4 receipts: a replay returns the stored receipt, changed content `replay_mismatch`) in its own table, never a snapshot or export.
- Telemetry bounds: config `telemetry` `{retention_days 1–90 (default 7), max_mib 1–1024 (default 160)}`, `max_mib` per installation and workspace (measured 2026-10-23 on win, taskq v4.6.30: 413,678 rows in 2.07 days, 10.6 MiB of blocks a day, 75 MiB in 7 days; default about twice that). The hourly prune drops blocks older than retention by receipt time; every accept drops that installation's oldest blocks over its budget; a block larger than the budget is `payload`. Each drop adds to that installation's known loss by cause (`capacity`, `retention`: blocks, rows, highest seq), which outlives the blocks. A full store acknowledges nothing, so the sender keeps its backlog. Blocks of an older store, or written by a rolled-back binary, get their seq range from their own payload on open; after a restore, rows the sender already delivered read as not received.
- Telemetry in `/data`: installation rows add `telemetry`: `off` (`telemetry not in grant`), `unknown` (`no telemetry block yet`, or every block pruned) or `ok` with `blocks`, `last_synced` (newest receipt time), `retained` `{blocks, rows, bytes, first_seq, last_seq, oldest_received, newest_received}` (receipt order), `pruned`, `holes` (seq ranges between stored blocks: never received, by a sender gap or a store restore; at most 32 listed, `holes_total`, `hole_rows`), `restarts` (a seq that goes back: the sender store was replaced) and `sender` (the newest block's counters, `unknown` with `status not reported by taskq` when missing; top-level `backlog_rows`, `backlog_bytes`, `gap_rows` repeat them). The TaskQ connection panel shows `Telemetry: last sync · backlog · gap · retained seq a–b`, then DashQ's removals and unreceived rows. `block=ID` (D7, also `dashq report --block=ID`) returns `telemetry_block` `{event_id, state, reason, blocks}`: each stored block of that event id within the caller's projected rows with installation, workspace, generation, `observed_at`, `received_at`, receipt, cursors and the accepted payload unchanged, plus its installation's coverage; an accepted block no longer stored is `unknown` (`accepted, no longer retained`), none `unknown`. Analysis views over blocks are later tasks. Production deploy to FRA needs owner approval.
- TaskQ resources (#160, taskq shared-resource-controls Project overlay): `taskq-resources/1` is a separate TaskQ schema; only a grant naming it may send it, else `scope`. Its payload is the `taskq.resources/1` projection (metadata allowlist, else `payload`) whose every target names the sending installation and generation, else `scope`. The newest record per installation and workspace replaces the last whole, in its own table, never a snapshot, so the board snapshot keeps the connection's readback. `/data` TaskQ installation rows add `project_limits`: `off` (`resources not in grant`), `unknown` (`no resources record yet`, `no status from this host`, future status time) or the D6 state of the payload's `observed_at` (status time; stale after 600 s, two board send intervals) with `targets` `{project_id, runtime_id, policy_schemas, current_revision, limit (null: no override), effective_revision, effective (null: unknown, never zero), blockers {code, knowledge}, completeness}`; the TaskQ connection panel lists them. ## D20. Profiling
Applies [built-in profiling](https://github.com/taskqorg/specq/blob/main/engineering/profiling.md).
- Measured operations, p95 budget and error budget (initial values; revise from the first production report): `http.page` and `http.data` 3 s, 1 %; `http.enroll` (D11 routes) 500 ms, 1 %; `http.answer` 15 s, 5 %; `http.resources` (D14 routes) and `http.configure` (D16) 500 ms, 1 %; `read.langfuse` and `read.taskq` 10 s, 5 %; `read.board` and `read.release` 3 s, 5 %; `read.serverq` 50 ms, 1 %; `read.tasklog` (D21) 500 ms, 1 %; `update.check` 15 s, 5 %; `update` 120 s, 5 %; `restart` (service reload after update) 30 s, 5 %. Times include response writing; cached source hits are not reads. A 5xx is a failure classed by its code, a 4xx is the caller's. Assets and 404 are not measured.
- Counters are always on in `serve`, `service run`, `report` and `update`: one record per finished operation `{at, op, ms, outcome, error}`. The error class is the source reason before any `:` detail, at most 40 plain characters; update and restart record only `failed`. No secrets, content, URLs or paths. `selftest` and tests write nothing.
- Store: `profile.jsonl` (0600, kept on prune) next to the config; past 4 MiB the writer keeps the newest half under a first line `{"pruned":true}`. A failed write never fails the operation.
- Detailed traces: env `DASHQ_TRACE=1` for the process run prints one line per operation to the process log (stderr); the process logs `profile: trace on`, the report shows `trace`. Each HTTP call is a span `trace #ID`: its source reads and the `enrollment` and `build` steps print as `step NAME MS ms at +OFFSET ms OUTCOME`, then the call total.
- Report: JSON `{schema 1, window_s, from, to, trace, store, samples, operations, unknown}`. Operations rank worst first by the larger of p95/budget and failure rate/error budget, then by variation (`cv`); each has count, p50/p95/max ms, outcome counts and error classes. A named operation without samples is listed under `unknown` with its reason; a missing store is `unknown`, a prune that dropped records inside the window makes the store `unknown` with the covered start, skipped corrupt records make it `incomplete` with their count. Never zero or ok.
