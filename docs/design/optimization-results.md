Accepted under D17. [AgentQ ACCOUNTING O1–O4](https://github.com/taskqorg/agentq/blob/main/docs/spec/ACCOUNTING.md) owns field meanings, populations and evidence. Reuse existing adapters, query/cache limits and authorized telemetry access.

## P1. Composition

Below the first-screen operational blocks, show Results with the existing 30 min / 2 h / 24 h period and client filter. Label the actual interval/timezone and source observation age. One compact outcome strip shows calls, compressed, passed and failed; a composition bar and common-scale time buckets retain exact counts. Selecting an outcome opens reasons in place. Client/profile rows expose recipe and the same outcome order.

Beside call history, show before/after volume on one zero-based byte scale, reduction and paired/observed sample coverage. Whole-task effect is separate supporting detail with its experiment identity, versions, sample size and uncertainty. The live filter never relabels a separate experiment as its own results. Coverage/evidence details retain safe source references. Preserve selection, focus, disclosures and scroll during automatic refresh.

## P2. Truthful states

Follow O1–O4: missing differs from zero; partial sources name missing coverage and cannot yield complete-period rates. A selected missing client remains visible with unknown values. Source freshness is not query time. Keep estimates, observed usage and task effects separate; raw byte reduction never becomes monetary savings. Normal pass-through reasons are neutral; optimization errors retain actionable evidence without implying task failure.

The accepted [reference](optimization-results-reference.html), [preview](optimization-results-preview.html) and [manifest](optimization-results-reference.sources.json) use synthetic counts, measurements and paired runs. Period multiplication/bucket allocation and Demo source/paired-run controls are fixture conveniences, not production aggregation or proof. Keep native RTK and headroom labels distinct; never borrow TaskQ task counters for optimization outcomes.

Real samples determine each bucket; do not interpolate missing events.

## Client observations and coverage

Preserved from D8 by #169; these are observation rules, not login probes. Placement follows [first screen](first-screen.md). A detected condition enters Attention only with the person/action test in D8; other records remain here with evidence.

Model activity per runtime and host; model usage per observed model with sample counts for each input/cache/output/reasoning field, never summed into a total; cost only when reported, else null. Clients (#131, `/data` `agents.clients` `{window_s, incomplete, rows}`): one row per D4.1 fleet installation and client `codex`, `claude-code` (producer `claude`) or `hermes` (other clients have no row; an installation naming none keeps one unknown row). Routing (`routing`, `reason`, `intended`, `intended_reason`) comes from `agentq.routing` of the installation's newest `agentq.installation` heartbeat (agentq#134: status.json `agents` as a JSON string); hooks per event (`state`, `last_ok_at`, `last_failure` `{at, error}`) from its `agentq.hooks`; MCP and configured hooks from the enrolled `agentq-snapshot/1` profile of the same installation (D16), else MCP is unknown (the heartbeat has no MCP state). Use over 24 h: the client's `agentq.compress` records (any adapter; records without an agent are shown apart), those with `agentq.adapter` `hook`, their `compressed` outcomes and bytes saved (`bytes_in` − `bytes_out`, null unless every such record has both), and `agentq.retrieval` calls of the installation (retrieval spans carry no agent). Producer reasons and errors pass only as short plain words. A heartbeat without these fields, an unreadable string, a value of the wrong shape (`agentq.routing` not an object of objects, `agentq.hooks` not a list of objects with `agent`) or a missing profile is unknown with its reason; a stale heartbeat or a stale or failed Langfuse read is last known (routing and hook badges read `Last known <state>`, never a current state); agent or session filters show no use.

AgentQ coverage (#116) items also name `client` and are current problems: an AgentQ-owned (onboarded) profile of an enrolled snapshot whose routing is `direct` or `bypassed`, or whose supported hooks are `missing`, `absent` or `partial` (`unknown`: a gap; a stale snapshot says last known); without agent or session filters, an installation with a fresh heartbeat whose host made model calls of a client in the period without any `agentq.compress` or `agentq.run` record for it (records without an agent count for every client), or whose host name (case-insensitive) has live attempts in a fresh taskq heartbeat but no model calls. Absence is asserted only on a fresh Langfuse read with no capped activity or agentq query and a confirmed board read; otherwise each fresh installation shows a gap `AgentQ coverage unknown` (or `TaskQ workers: liveness unknown`) with the reason. These #116 items read enrolled snapshots only. Client use (#131), without agent or session filters and with a fresh heartbeat: a D8.4 client with hooks (enrolled `registered`, or any heartbeat hook record) or MCP (enrolled `registered`) configured and with activity (model calls in the period, or a hook run in 24 h), but without any `agentq.compress` record of it in 24 h (records without an agent count for it), or without any `agentq.retrieval` record of its installation in 24 h, is a current problem `<client>: hooks configured, no compress records in 24 h` or `<client>: MCP configured, no retrieval calls in 24 h`; a failed or capped 24 h read makes it the gap `<client>: AgentQ use unknown`; an existing #116 `no compression records` item for that client is not repeated.
