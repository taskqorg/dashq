## Projection and compatibility boundary (A3)

D7 remains schema 2. `src/data.rs` adds `servers` through the shared document builder used by `/data` and `report`. `servers.rows` is an array; each row has `id`, `host`, `workspace`, `installations`, `entities`, `source`, `pilotq_selector` and `pilotq_url`. Entities hold typed `inventory`, source state and deterministic trends. A server without inventory remains a row with an explicit unknown reason (R2/D6), not fabricated measurements.

`pilotq_selector` is the exact JSON string `[workspace, machine/kind]`; legacy workspace is null. D30 hashes its UTF-8 bytes with FNV-1a 64-bit into 16 lowercase hexadecimal digits. For `["example","invented-fresh/native"]`, the link payload is `server-0ad79b58009edbd1`. Only configured `https://t.me/BOT` targets use `?start=` and remove the pending-selection label. This agrees with the PilotQ contract referenced in the [existing evidence](../design/evidence/servers/README.md#telegram-chat-link-272). Source inspection of [PilotQ `src/servers.rs` at merged commit `89af7b1725ed539d995ec325696a7b8752438df8`](https://github.com/taskqorg/pilotq/blob/89af7b1725ed539d995ec325696a7b8752438df8/src/servers.rs) confirms that `read` accepts a report containing `servers.rows` as an array. Its `view` reads the same row workspace, host, source time/state/reason and entity inventory/source/trends; `link_payload` hashes the exact selector bytes with the same FNV-1a algorithm. `call` limits the read to the remaining caller deadline or 30 seconds, whichever is shorter. This establishes source-shape compatibility, not successful installed execution. PM separately confirms that the installed PilotQ 0.2.45 reader accepts this shape; the installed official DashQ 0.18.1 lacks D30, so the installed pair cannot yet provide this inventory.

D11 scope, current generation, revocation and retirement filtering remain in `enroll::server_inventory`. R1/R7 permit typed inventory only in this scoped projection; no raw telemetry, private configuration, command arguments or stderr are included in this report.

## Bounded report diagnosis

The cold `report` command creates a new cache and calls `App::doc`, which calls `document` with background reads disabled. It waits for optional source reads before building the server projection. In each project thread, board, release and optional TaskQ snapshot reads run sequentially; two CLI-release comparisons also run sequentially afterwards. Langfuse query families run concurrently, but each may paginate. The D4 HTTP timeout is 10 seconds **per call**, not a report-wide deadline. D30 inventory is another synchronous store read in this mode. Consequently a wrapper deadline can expire even though individual calls are bounded; `/data` background refresh behavior does not establish a cold report bound.

A temporary, invented-config process probe replaced curl with a stdin-consuming stub that takes 0.35 seconds and returns timeout. With one configured board and no TaskQ or Langfuse, a 0.5-second outer bound expired; a 3-second bound completed in 1.46 seconds, exit 0, with `servers.rows` an array. The four sequential calls explain the elapsed time. Stderr was discarded and no live config or credentials were used. This reproduces the timeout mechanism, not a production fix or a trace of the reported pds18 failure. The synthetic probe does not identify the internal wait seen by PM below. No timeout promise, source behavior or scope is changed in a version-only release.
