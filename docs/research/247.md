# TaskQ runtime release prerequisite for Fleet

## Question

Does a published TaskQ release contain taskqorg/taskq#2094, and which released interfaces can [Fleet #244](https://github.com/taskqorg/dashq/issues/244) use for A2–A5?

Scope: [#247](https://github.com/taskqorg/dashq/issues/247), read-only upstream verification. This records evidence; it changes no product decision, asset pin, installation or deployment. DashQ R1, R2, D4.2, D10 and D18 apply: metadata only, unknown remains unknown, and release availability is separate from running or verified health.

## Findings

### A2: released version and usage interfaces

All TaskQ source references in this section are from v4.6.65's exact commit.

**CLI versions (Fleet A5).** The [heartbeat contract](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/docs/design/host-service.md#L264) specifies `cli <bin> <version>` for installed runtime binaries (`claude`, `codex`, `agy`), with `unknown` on an unread version. This is distinct from `version <v>`, which is TaskQ's version.

The [runtime probe and conversion](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/runtime.rs#L2890) expose `runtime`, `path`, `version`, login and account metadata. Missing installations have null path/version; `clis_versions` includes installed binaries only, maps unread versions to `unknown`, and deduplicates aliases such as codex-app by binary. [Heartbeat generation](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/service.rs#L1763) emits these lines; the [released regression](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/service.rs#L7386) covers a known Claude version and unknown Codex version. This test was inspected, not executed here.

[Service status publication](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/main.rs#L1514) caches runtime probes for 300 s and sets `clis` from them. `status.json` uses `agents: {at, rows}`, with each row's `runtime` and nullable `version`; the [status assignment](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/main.rs#L1619) preserves that envelope. Do not assume these local fields occur in every `taskq status --json` board snapshot or D11 projection. The [enrolled host projection](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/enrollment.rs#L446) reads these rows for login observations, without copying CLI versions into that observation.

**Usage export (Fleet A2–A3).** [The active CLI dispatcher](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/profile.rs#L1133) routes `taskq profile export --since 24h` (also `7d`) to [telemetry export](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/telemetry.rs#L516). It emits JSON lines:

- Header: `schema: 2`, `coverage: "committed-import-cursor-snapshot"`, `since_ms`, and `sources.universal` / `sources.legacy` with sample and retention evidence.
- Rows: `{source, seq, id, received_ms, observation}`. Universal pages are consumed in batches of 1024; legacy rows are filtered against the same committed import cursor to avoid duplication.
- The read-only store snapshot is released before output. Unavailable or corrupt sources fail export before any JSON is printed. Unknown timestamps remain included with a reason under a time filter.

The [released export documentation](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/docs/design/profiling.md#L79) describes this schema-2 boundary. Its later schema-3 column list refers to the older semantic export, not the active universal CLI envelope; consumers must inspect `schema` rather than assume the old format.

[Cargo.lock](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/Cargo.lock) pins CoreQ v0.19.1 at `17eb4b9f7894b5550e6b30e191302b905a360c0b` and AgentQ runtime at `b2c50de65cd6207acd33f9298bd0f091b994fe33`. The preserved runtime successor is AgentQ `agent`; do not assume the earlier CoreQ adapter module name remains the import path.

The pinned [agent.turn observation encoder](https://github.com/taskqorg/agentq/blob/b2c50de65cd6207acd33f9298bd0f091b994fe33/runtime/src/agent.rs#L985) defines `product`, `version`, `operation`/`kind: "agent.turn"`, `started_ms`, `duration_us`, `outcome`, `error`, `project`, `runtime`, `account`, nullable `task`/`attempt`, `input_tokens`, `cache_read_tokens`, `cache_write_tokens`, `output_tokens`, `model`, `route`, `limit_used_percent`, `limit_resets_at`, `limit_window` and per-field `unknown` reasons. Its [caller context](https://github.com/taskqorg/agentq/blob/b2c50de65cd6207acd33f9298bd0f091b994fe33/runtime/src/agent.rs#L675) owns project, task/attempt, route and account codes. The [CoreQ field allowlist](https://github.com/taskqorg/coreq/blob/17eb4b9f7894b5550e6b30e191302b905a360c0b/src/telemetry.rs#L41) accepts account, token and limit fields. These references establish the available schema, not that every TaskQ path emits complete agent.turn rows.

TaskQ's [stage usage reader](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/runtime.rs#L309) uses AgentQ `agent::usage`; its [semantic mapping](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/telemetry/semantic.rs#L64) exports project, host, task, attempt, runtime, stage, token split, model and explicit missing-field reasons. Stage rows do not supply account or limit fields. They cannot substitute for complete per-account observations.

**Cadence and workers (Fleet A4).** The same [semantic mapping](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/telemetry/semantic.rs#L64) preserves transition project/task/host/runtime, `from`, `to`, `entry`, `started_ms` and previous-state duration. [Worker observation fixtures](https://github.com/taskqorg/taskq/blob/0c57f08f6ff8c9446e7127ab9bf05df80a439450/src/telemetry/semantic.rs#L342) cover worker `spawn` with host/project/runtime/role/task/attempt. Fleet must define its cadence measure and deduplicate stable identities; stages, transitions and spawns are separate observations, not interchangeable task totals.

### Acceptance boundary and remaining gaps

| Item | Evidence and conclusion |
|---|---|
| #247 A1 | Pass: published non-draft v4.6.65 contains the exact required merge. |
| #247 A2 | Pass: released heartbeat/status fields, export envelope and pinned usage schema read; immutable references recorded above for #244 A2–A5. |
| #244 A2 | Schema supports project/task/account token fields, but complete 24 h/7 d coverage, retention and delivery through D11 need separate qualification. Stage rows alone cannot prove per-account totals. |
| #244 A3 | Agent schema supports percent/reset/window and unknown reasons. Live per-account availability and D11 delivery remain unverified. A quota hold is not percent used. |
| #244 A4 | Transition/worker observations exist; the Fleet cadence definition, complete host coverage and aggregation remain implementation work. |
| #244 A5 | Heartbeat and local status provide CLI versions. Newest-version source, freshness, D11 transport and drift comparison remain implementation/qualification work. |

No released binary was downloaded or executed, no host health was inferred, and no release/deployment was performed. Live Q1/Q6/Q15 and usage baseline work was explicitly carried to [taskq#2111](https://github.com/taskqorg/taskq/issues/2111) by [#2094](https://github.com/taskqorg/taskq/issues/2094); this report does not claim that qualification. CoreQ's separate release prerequisite for #244 is outside this task.

## Options

- Use v4.6.65 as the verified TaskQ release prerequisite. Pro: exact ancestry and published interfaces are established. Con: Fleet still needs its ingestion and live-data qualification.
- Keep waiting for another TaskQ release. Pro: a future release may close further transport gaps. Con: waiting adds no evidence that the already published prerequisite lacks the required merge.

## Verdict

Confirmed: v4.6.65 satisfies #247's release prerequisite. This is not acceptance of the Fleet view or its live data paths.

## Recommendation

Use the exact release/source references above in #244. Continue Fleet implementation under its existing acceptance, keeping incomplete coverage unknown (R2) and update/restart authority unchanged (D18). No new product decision is proposed.
