# DashQ report timeout investigation

## Question

Which internal wait caused the installed DashQ report to exceed PilotQ's 30 s deadline in [#274](https://github.com/taskqorg/dashq/issues/274)? [#276](https://github.com/taskqorg/dashq/issues/276) authorizes source inspection, synthetic reproduction and a bounded phase instrument, not live configuration access or product changes (A1–A6).

## Findings with evidence

### Observed production symptom; cause still unknown

The [PM observation](https://github.com/taskqorg/dashq/issues/274#issuecomment-6677324179) records DashQ **0.18.1**, PilotQ **0.2.45**, TaskQ **4.6.87**; deadline **30 s**, elapsed **30.03 s**, **0 stdout bytes**. The PM reports curl at 2.14 s and TaskQ at 3.20 s; from **6.41 s** until termination only DashQ was observed. The PM terminated and reaped the dedicated probe group; no service was stopped. These are supplied observations, not measurements repeated by this worker.

This establishes an unfinished report, with no observed child process during the last 23.62 s. It does **not** distinguish local I/O, SQLite work or contention, decoding, aggregation, serialization, stdout blocking, or an unobserved short child. A process list samples liveness, not its call stack. Neither the FIFO below nor the absence of children establishes the production cause (R2/D6; specq § Evidence / Remediation).

### Code mechanism and wait boundaries

Read the following paths at each revision above; line positions differ between versions.

| Phase | Source mechanism | Limit and diagnostic meaning |
|---|---|---|
| Config / enrollment open | `src/main.rs`, `main` report arm; `Enroll::open_with`; `Store::open` | Config/key/file reads; SQLite checks, schema/setup. SQLite busy timeout is 10 s per busy handler, not a whole-report limit. |
| Optional sources | `App::doc` (0.18.1), `App::document(..., false)` (candidate); `src/source.rs`, `Cache::get` | New process, empty cache. Scoped threads join Langfuse and each configured repository. Per repository: board, release, then TaskQ snapshot sequentially; repositories run concurrently. |
| HTTP / pagination | `source::exchange`, `langfuse`, `observations` | curl has `--max-time 10` per call (D4). Langfuse query families run concurrently, pages within a family sequentially. A row cap is not a total time budget; empty pages with distinct cursors do not advance that row cap. |
| TaskQ | `source::taskq_run` | 10 s status limit; independent of preceding board/release calls. Parent joins the stdout reader after child exit, and the stderr reader on unsuccessful exit, so a descendant holding a pipe can also hold a join. No such descendant was established by PM's probe. |
| ServerQ | `source::serverq` | `std::fs::read_to_string` then JSON parsing, no deadline or regular-file restriction. Runs after the source thread scope joins. |
| Local TaskQ logs | `agent_work::read` | `std::fs::read`, then line decoding and collection; no whole-read deadline. |
| Projection / resources / findings | `enroll::projection`, `resource_samples`, `finding_samples`; `store::project` | SQLite queries and snapshot decoding, synchronously on report. Projection uses a write transaction to mark rendered receipts projected; the existing report is not an entirely read-only SQLite connection. |
| Stages / Fleet | 0.18.1 `src/enroll.rs`, candidate `src/enroll/projection.rs` | Reads and decodes stored telemetry; stage memo/cache starts cold. Fleet's retained-row cap does not bound all preceding block decoding. Candidate report also reads D28 records synchronously. |
| Inventory / observations | candidate `server_inventory`, `observations` | Additional synchronous report work. Inventory reads scoped inventory history; not present in v0.18.1. |
| CLI releases | `runtimes::clis`, `source::cli_release` | Sequential cache reads after enrollment work; each HTTP request has its own limit. |
| Build / block / assets / export status | `data::build`, `telemetry_block`, `App::assets`, `export::status` | Local aggregation; candidate assets may add HTTP calls. No whole-document deadline. |
| Serialization / stdout | report's `println!("{}", App {...}.doc(...))` | Document must return before JSON formatting/output starts. Zero output is therefore compatible with every earlier phase, and can also occur before the first successful output write. |

D4's background browser behavior does **not** make the candidate CLI asynchronous: `doc` explicitly selects `background=false`. Both versions wait for a complete document. The 10 s HTTP timeout cannot be read as a 10 s or 30 s report deadline. The report arm does not call `profile::begin`; existing `profile::step("enrollment"/"build")` requires such a span. `DASHQ_TRACE=1` additionally writes stderr and therefore is not the approved collector for A3.

### Synthetic reproduction and phase measurements

[phases.py](276/phases.py) copies each exact Git revision to a new private temporary directory and inserts fixed phase markers **only in that disposable copy**. Tracked product sources, assertions, contracts, installation and services remain unchanged (A4). It builds with the revision's own locked dependencies; these are instrumented debug source builds, not official release artifacts.

The synthetic input is a private 0600 invented config, no configured remote sources, no enrollment database/key and a private FIFO as the ServerQ report. No writer opens the FIFO. Both versions reach `source::serverq` and wait in the local file read until the external one-second probe deadline kills the dedicated group. Then the fixture alone is replaced with a tiny regular schema-1 report and the same binary completes. This is a controlled input experiment, **not a product fix** or a passing live acceptance.

Environment: Linux x86_64, rustc 1.99.1 (`58cf8f9c3`, 2026-10-13), Python 3.14.4. Locked debug builds completed in 22.47 s / 27.75 s respectively. Raw metadata evidence: [0.18.1](276/0.18.1.jsonl), [candidate](276/0.18.2-candidate.jsonl).

| Version | FIFO: elapsed / output | Last phase at deadline | Regular-file control: elapsed / output | Internal phases in control |
|---|---|---|---|---|
| 0.18.1 source | 1003 ms / 0 bytes; killed | `serverq`, entered at 0 ms | 18 ms / 7015 bytes; exit 0 | sources 0; serverq 0; tasklog through CLI releases 1; build 1; block/export/serialization 4; done 5 ms |
| 0.18.2 candidate source | 1004 ms / 0 bytes; killed | `serverq`, entered at 0 ms | 17 ms / 7568 bytes; exit 0 | sources 0; serverq 0; tasklog through CLI releases 1; build 1; block/assets/export/serialization 4; done 5 ms |

Times in phase records are milliseconds since the first in-process marker; adjacent markers bound the preceding phase. Wall time also includes process startup/collection. Millisecond resolution can show zero for short work. An entered phase without its successor is unfinished/unknown, never a successful zero-duration phase (R2). Absent enrollment/remote sources make those control phases trivial; these measurements say nothing about production store volume or network latency.

The experiment **confirms** a specific internal mechanism capable of the observed shape: a synchronous, unbounded local file read after remote children have exited, before any report output. It does **not** establish that production's configured input was a FIFO, nor even that production reached ServerQ. Multiple mechanisms fit PM's observations. No worker opened live configuration or contacted the production report endpoint.

The collector emits only allowlisted phase names, nonnegative elapsed milliseconds, deadline, timeout flag, exit status, stdout byte count and collection completeness. ### Passive recipe for PM

[passive.py](276/passive.py) observes only the supplied probe PID's Linux `/proc` thread CPU counters, scheduler state and kernel wait channel. It never launches, signals, attaches a debugger to, changes or installs the target. It does not open its config, database, key, memory, file descriptors, command line, environment, mappings or stack. Kernel wait symbols are mapped through an exact allowlist to fixed classes; arbitrary symbols and the `stat` process name are discarded. No perf session, raw perf.data, symbol dump, stack payload, path or target PID is exported (R1/R7). Python and the native `/proc` interface are sufficient; installed perf is not needed for this narrower observation and no perf permission change is requested.

PM adds this observer to the **existing authorized dedicated 30 s official-report probe supervisor**, once that supervisor has the report process PID. Do not observe the service or substitute a rebuilt executable. The existing supervisor still discards report output, counts bytes and owns target/group termination and reaping at 30 s. Start sampling promptly; use 20 s (maximum permitted by the tool: 25 s), so the observer finishes before the existing deadline:

```sh
# PM only. PROBE_PID is supplied by the existing supervisor, never discovered via argv.
python3 docs/research/276/passive.py "$PROBE_PID" --seconds 20
```

The observer samples that PID's threads every 250 ms, at most 256 threads per poll. It checks process start time before every poll and stops if PID identity changes; it does not follow descendants or newly reused PIDs. If the installed launcher waits on another process rather than replacing itself, `child_wait` describes the selected process only; the existing supervisor must identify the actual report PID within its current authority. Do not infer that its child is blocked in a source phase. Process start time is an internal identity check and is never exported.

Result fields: schema, observation coverage, end reason, elapsed milliseconds, thread-sample/missing/capped counts, summed sampled thread CPU milliseconds and fixed scheduler/wait-class counters. Counters are **thread samples**, not independent operations or elapsed phase durations. CPU is a tick-resolution lower observation over intervals, excluding each thread's first sample and exited threads' unsampled work. `observed` means classified samples, never report/source health. No samples is `unknown`; permission-masked wait channels (`0`), unknown symbols, missing reads, thread caps or identity change retain `incomplete`/`unknown` (R2/D6). A vanished target ends observation; neither that nor a zero CPU delta proves successful report completion.

Interpretation, without guessing a source phase:

| Evidence | What it narrows | What remains unknown |
|---|---|---|
| `fifo_open` | Sleeping while opening a FIFO, as in the synthetic file-read mechanism | Which configured input/file; ServerQ versus another file open |
| `pipe_read` / `pipe_write` | Blocking pipe I/O | Which pipe/reader/writer; whether report output or a source subprocess |
| `futex` | Userspace synchronization wait | Lock owner; cache, store mutex or thread join; an active worker may coexist |
| `child_wait` | Selected process waiting for a child | Child's internal phase; launcher versus report reader |
| `timer` | Timer wait | Retry/backoff versus another timed operation |
| `io_wait` / uninterruptible scheduler state | Kernel I/O wait evidence | Device, file or query identity; no path is inspected |
| `runnable` plus increasing CPU | CPU work during observed intervals | SQLite execution, JSON decode, aggregation and serialization share this class |
| `unavailable` / `other_wait` | Unsupported/hidden wait evidence | No phase claim is justified; do not request new access automatically |

These classes add information missing from the PM's old process-count probe; this is not another attempt to collect empty internal markers. The sampler cannot establish an exact userspace source phase by itself. PM should return only the allowlisted JSON alongside the existing version/deadline/output-count/cleanup metadata. The worker will relate that observation to the source mechanisms above, preserving ambiguity when more than one fits.

### Synthetic filtering and cleanup proof

`PYTHONDONTWRITEBYTECODE=1 python3 docs/research/276/test_passive.py` passed two checks on Linux x86_64/Python 3.14.4:

- A fake proc tree contains an invented private process name and unknown kernel symbol, then reuses the PID with a different start time. Export contains only `other_wait`, marks coverage incomplete and stops at `identity_changed`; neither private canary nor PID is exported. Masked channels map to `unavailable`.
- Real disposable Python processes block opening a private FIFO or spin on CPU. Each observation exits at 400 ms while leaving its target alive. Only the test supervisor then kills/reaps each synthetic target; the observer owns no child/session to clean up. Sampling the reaped target returns unknown. First measured FIFO run: 8 thread samples, 7 `fifo_open`, 1 `runnable`, 10 ms sampled CPU. CPU run: 8 `runnable` samples, 350 ms sampled CPU. These are synthetic process checks, not DashQ production measurements.

The new checks protect distinct risks absent from `test_probe.py`: leaking native process/kernel names, attributing a reused PID to the original target, and accidentally terminating a passively observed target. They do not change any existing assertion or product decision (§ Testing / Before adding or changing a test). Production proc visibility remains untested by the worker; failures must remain unknown.

### Exact missing capability and isolated proposal

If the passive result is CPU work, a generic futex, or hidden wait evidence, it cannot distinguish `projection` from `stages`, `fleet`, `build` or serialization. Exact discrimination needs either source-correlated userspace sampling of the **unchanged official artifact** (usable symbols/unwind information plus already-permitted perf sampling), or source-boundary markers on a diagnostic executable. Merely having perf installed proves neither permission nor usable symbols. Do not collect raw perf stacks/files or widen perf permissions under this task's current authority. No stripped/unstripped or perf-availability claim is made without PM evidence.

A concrete fallback for an **owner decision**, not authorization granted by this report:

1. PM creates a consistent disposable offline copy of the minimum affected store/input set, using a read-only source connection/backup and keeping any necessary config/key private under PM custody. Copy creation reads live storage and briefly holds a source snapshot; authorize that effect explicitly. The worker receives no private copy, config, key, path, report content or raw stack.
2. PM uses a private directory and network isolation; no service, release selection, grants, installed executable or live database is changed. Run the unchanged official executable against a writable disposable copy first under the existing 30 s bound, discarding stderr/report content. Normal store migrations/receipt projection can affect **only the copy**. Require the offline copy to reproduce the live symptom before drawing a phase conclusion; missing remote data, cold caches and the copy operation can change behavior.
3. Only if separately approved, PM runs an exact-source diagnostic with the fixed boundary markers against an equivalent fresh copy, never against live data and never installed. Export only phase names/times, source identity, deadline, output bytes and cleanup status. Differences from the official artifact remain explicit; diagnostic overhead and store-copy equivalence limit inference.
4. PM terminates/reaps the dedicated groups and removes its private disposable copies/config/key. This reverses the experiment without restoring or touching live state. No owner choice is needed to discard the diagnostic; no production remedy follows automatically.

Options for that later owner decision: permit this isolated-copy diagnostic (gain: source-phase evidence without executing a rebuilt binary on live data; cost: private-copy handling and possible failure to reproduce), or retain unchanged-artifact observations only (gain: preserves the current access boundary; cost: exact userspace phase may remain unknown). Recommend the copy route **only if** the new passive observation cannot resolve the causal ambiguity and the owner explicitly approves its effects. Until then the next step is PM's passive observation, not an installation, permission change or guessed root cause. A5 and #274 A3 remain open.
